# Experiment A · Phase 2 — Experiment Protocol

**Written:** 20 November 2026, against the Phase 1 audit (`implementation_audit.md`).

**Primary research question.** How reliably can an offline-first, multi-tenant
healthcare application preserve data integrity and achieve eventual consistency
under intermittent connectivity, retries, concurrent submissions and application
interruptions?

**Scope, fixed by the audit.** Only `EHRRecord` is offline-capable. Every
scenario below concerns Health Wallet records. Nothing here measures appointment,
prescription, SOS, lab-booking, pre-order or vitals synchronisation, because no
offline path exists for them.

---

## 0. Rules that govern every scenario

1. **HTTP 200 is not evidence.** Every assertion is made against persisted
   database state, read back through a direct SQLAlchemy session, not through the
   API that just wrote it.
2. **Isolated PostgreSQL only.** SQLite is not used for any concurrency
   scenario, and is not used as a substitute anywhere in this experiment.
3. **Synthetic data only.** All patients, households and records are generated by
   the harness. No real patient data. No production database.
4. **Positive control required.** Each scenario group runs a control that must
   pass. If the control fails, every result in that group is reported
   `INCONCLUSIVE`, never `PASSED`.
5. **Four verdicts:** `PASSED`, `FAILED`, `INCONCLUSIVE` (5xx, harness error, or
   failed control), `NOT_APPLICABLE` (the capability does not exist — recorded,
   not silently skipped).
6. **Per-batch ledger.** For every batch: submitted, persisted, unique persisted
   UUIDs, duplicates, missing, unexpected, overwritten, cross-tenant. Computed
   from database state.
7. **Provenance on every run:** Git SHA, PostgreSQL version, Python and library
   versions, Alembic revision, UTC start and finish, the exact command.

### The integrity ledger, defined

For a batch `B` submitted by patient `p`, with `U(B)` the set of client UUIDs in
`B`:

| Quantity | Definition |
|---|---|
| `submitted` | `|B|` |
| `persisted` | rows in `ehr_records` whose `client_uuid ∈ U(B)` |
| `unique_persisted` | distinct `client_uuid` among those rows |
| `duplicates` | `persisted − unique_persisted` (extra rows for the same UUID) |
| `missing` | `|U(B)| − unique_persisted` (UUIDs submitted but absent) |
| `unexpected` | rows whose `client_uuid ∉ U(B)` appearing in `p`'s wallet during the scenario window |
| `overwritten` | rows where `client_uuid ∈ U(B)` and the stored `content` differs from the submitted `content` for that UUID |
| `cross_tenant` | rows with `client_uuid ∈ U(B)` whose `patient_id ≠ p` |

**Integrity holds for a batch iff** `duplicates = 0 ∧ missing = 0 ∧
unexpected = 0 ∧ overwritten = 0 ∧ cross_tenant = 0`.

## A · Normal synchronisation

**Control (A0).** One record, one submission, stable connection.
Expected: `persisted = 1`, ledger clean, `synced[]` contains the UUID.
**If A0 fails, group A is INCONCLUSIVE.**

| # | Initial state | Operation | Expected | Failure condition | Integrity assertion |
|---|---|---|---|---|---|
| A1 | empty wallet | submit 1 record | 1 persisted, in `synced[]` | anything else | ledger clean |
| A2 | empty wallet | submit 10 in one batch | 10 persisted, 10 in `synced[]` | any missing or duplicate | ledger clean |
| A3 | empty wallet | submit **100** (the schema cap) | 100 persisted | 422, or any missing | ledger clean |
| **A3b** | empty wallet | submit **101** | **predicted FAIL: 422, 0 persisted** (audit A1) | anything persisted, or a non-422 error | `persisted = 0` and the client can distinguish this from a transient failure |
| **A3c** | 150 records queued locally | run the client's own `pushUnsynced` logic | **predicted FAIL: permanent deadlock** | — | the queue never drains across repeated attempts |
| A4 | empty wallet | submit records with `record_date` = now, +10 years, −10 years | **predicted FAIL: all accepted unvalidated** (audit A7) | — | stored `record_date` equals what was sent; wallet ordering is wrong |
| A5 | empty wallet | one record of **each** of the 6 types | 6 persisted, types preserved | any type rejected or altered | ledger clean |
| A6 | empty wallet | submit a record carrying `payload` | accepted; `payload` stored | — | **NOT_APPLICABLE for the mobile path** — the Hive model has no payload field (audit A6). Tested here against the API contract only, and the gap recorded |

**Reproducibility:** fixed UUID list per scenario, written to a fixture file so
the same batch is replayable byte-for-byte.

## B · Duplicate delivery

**Control (B0).** Submit a batch, verify clean, then re-read — count must not
change without a second submission.

| # | Initial state | Operation | Expected | Failure condition | Integrity assertion |
|---|---|---|---|---|---|
| B1 | 10 persisted | resubmit the identical batch | all 10 in `duplicates[]`, `persisted` unchanged | any new row | `duplicates = 0`, `persisted = 10` |
| B2 | 1 persisted | submit the same UUID 5 times sequentially | 1 row throughout | row count > 1 | `unique_persisted = 1` |
| B3 | 10 persisted | resubmit after a simulated client timeout (no ack consumed) | all acknowledged as duplicates | client would retry forever | row count stable; a second retry also returns duplicates |
| B4 | 10 persisted, client state discarded | resubmit as a "restarted client" | all duplicates | any new row | `persisted = 10` |
| B5 | 10 persisted | resubmit with the **same UUIDs but different content** | **rows unchanged** (first write wins; there is no update path) | any content changed | `overwritten = 0` — and the behaviour is documented as first-write-wins, not as conflict resolution |

## C · Intermittent connectivity

Faults are injected at the transport, not by mocking the client, so the server
sees exactly what a dropped connection produces.

| # | Interruption point | Operation | Expected | Failure condition | Integrity assertion |
|---|---|---|---|---|---|
| C1 | before the request is sent | queue 10, no network | 0 persisted, 10 still queued | any persisted | `persisted = 0` |
| C2 | mid-request, before server commit | abort the connection partway | 0 persisted | partial persistence | `persisted = 0`, then a retry persists exactly 10 |
| **C3** | **after server commit, before the response reaches the client** | commit, then drop the response | **10 persisted; client still has them queued; retry returns all 10 as duplicates; no second copy** | any duplicate row, or the client retrying forever | `duplicates = 0`, `unique_persisted = 10` — **this is the scenario the whole design exists for** |
| C4 | reconnect | after C2, retry | 10 persisted, ledger clean | any missing | ledger clean |
| C5 | repeated flapping | 5 cycles of connect/abort around one batch | exactly 10 rows after convergence | any count other than 10 | `unique_persisted = 10`, `duplicates = 0`; record the retry count to convergence |

## D · Concurrency — **PostgreSQL only**

SQLite serialises writers and cannot exercise these. All run against the isolated
PostgreSQL container.

| # | Initial state | Operation | Expected | Failure condition | Integrity assertion |
|---|---|---|---|---|---|
| D1 | empty | **10 concurrent** identical 25-record batches | exactly 25 rows | any duplicate, any 5xx | `duplicates = 0`, `unique_persisted = 25`, 0 server errors |
| D2 | empty | 4 concurrent batches **overlapping** by 50% (A∪B share half their UUIDs) | exactly `|A ∪ B|` rows | any duplicate or missing | ledger clean over the union |
| D3 | empty | 2 concurrent batches sharing **one** UUID, different content | 1 row for that UUID; one of the two contents, deterministically first-write-wins | 2 rows, or a 5xx | `unique_persisted` correct, `duplicates = 0` |
| D4 | 1 persisted | 8 concurrent resubmissions of that UUID | 1 row | any growth | `persisted = 1` |
| D5 | empty | 20 concurrent single-record `POST /ehr/record` calls, all the same UUID | 1 row, 20 × HTTP 2xx | any 5xx, or > 1 row | tests the single-record path's `IntegrityError` branch, which D1 does not reach |

**Each D scenario is repeated 10 times** (sample size reported) because
concurrency outcomes are not deterministic. Rates are reported as
numerator/denominator with a Wilson 95% interval.

## E · Concurrent change semantics — **reframed**

**The audit established that no conflict resolution exists** (A3): wallet records
are append-only, there is no update endpoint, no version column and no merge.
Scenario group E therefore **cannot measure conflict-resolution correctness**.
What it can and does measure is whether the append-only model holds, and what it
gives up.

| # | Operation | Expected | Verdict kind |
|---|---|---|---|
| E1 | "local update vs server update" of one record | **NOT_APPLICABLE** — no update path exists for either side | `NOT_APPLICABLE`, documented |
| E2 | two offline edits of the same logical fact from one device | two **separate** records, both persisted, no link between them | `PASSED` if both persist and neither overwrites; the accumulation of a wrong and a corrected entry with no linkage is recorded as a design cost |
| **E3** | server-side change after a client has pulled | **predicted FAIL — never reflected locally** (audit A4) | measured against the client's own `pullRemote` skip logic |
| E4 | two devices, same account, same UUID | 1 row (D3 covers the race); both devices converge to `synced = true` | `PASSED` / `FAILED` |
| E5 | two devices, same account, **different** UUIDs for the same fact | 2 rows — the system cannot tell they are the same fact | documented design cost, not a defect |

## F · Recovery

| # | Initial state | Operation | Expected | Failure condition | Integrity assertion |
|---|---|---|---|---|---|
| F1 | 20 queued | kill the sync mid-flight, restart, sync again | exactly 20 rows | duplicates, or records lost | `duplicates = 0`, `missing = 0` |
| F2 | 20 queued, 10 already committed server-side but unacknowledged | restart and sync | 20 rows; the first 10 return as duplicates | any duplicate row | `unique_persisted = 20` |
| F3 | partial per-item commit after an `IntegrityError` | resume | all UUIDs present exactly once | any missing | ledger clean |
| F4 | 7 days of accumulated records (**120 records**) | reconnect and sync | **predicted FAIL via A1** — over the 100 cap | — | measures the real-world consequence of A1 |
| F5 | durability | write locally, hard-stop the process, reopen the box | all records present and still encrypted | any loss | local row count preserved |

## G · Data isolation

| # | Initial state | Operation | Expected | Failure condition | Integrity assertion |
|---|---|---|---|---|---|
| G1 | patients A and B | each syncs 10 records | A sees only A's, B only B's | any cross-visibility | `cross_tenant = 0` both ways |
| G2 | A owns profile P | B submits a batch with `family_profile_id = P` | **403, nothing persisted** | any row written | `persisted = 0` |
| G3 | A owns profile P | A submits with `family_profile_id = P` | persisted and scoped to P | rejected | ledger clean |
| G4 | A's queue contains one record for a **deleted** profile | A syncs the whole queue | **predicted FAIL — entire batch blocked** (audit A2) | — | `persisted = 0` for all items, including valid ones |
| **G5** | A has persisted UUID `X` | **B submits a record with `client_uuid = X`** | **uncertain — the unique index is global, not per-patient.** Expect B told "duplicate" and **B's record silently lost** (audit P7) | B's record persisted under A, or B's record lost while reported synced | `missing` for B must be 0; if it is 1 while B was told the record synced, that is **silent cross-tenant record loss** |
| G6 | — | submit with `patient_id` injected in the payload | ignored; `patient_id` taken from the token | any row under another patient | `cross_tenant = 0` |

**G5 is the scenario most likely to produce a novel finding** and must not be
skipped.

## Harness requirements (Phase 3 contract)

1. Isolated PostgreSQL container; refuses to run against SQLite or any managed
   host.
2. Synthetic patients, households and records; fixed UUID fixtures for
   replayability.
3. Transport-level fault injection — abort before send, mid-send, and after the
   server commits but before the response is delivered (C3 requires reaching
   inside the commit boundary, which the harness does by committing in a request
   it then abandons).
4. Real concurrent execution via threads against PostgreSQL.
5. Ledger computed from database state for every batch.
6. Structured per-scenario logging with the four verdicts, plus the control
   result for each group.
7. Repeat counts per scenario, with rates reported as numerator/denominator.
8. Provenance recorded in a summary JSON.

**A test is not `PASSED` if its group's control failed.** **An HTTP 200 is not
`PASSED`.** Only the ledger decides.
