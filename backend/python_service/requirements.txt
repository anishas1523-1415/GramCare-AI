# Core Framework

# CHANGED 2.11.7 -> 2.13.4 (dependency audit). google-genai==2.10.0 requires
# pydantic>=2.12.5,<3.0.0, which 2.11.7 cannot satisfy. Previously this went
# undetected because `google-genai` was floor-pinned (`>=1.65.0`) and
# installed in a separate pip invocation from the rest of this file, so pip
# silently upgraded pydantic past the stated 2.11.7 pin instead of failing
# loudly. 2.13.4 is within fastapi 0.115.12's accepted range
# (`<3.0.0`, excluding a handful of unrelated 2.0.x/2.1.0 point releases),
# so no other code is affected.
pydantic==2.13.4
# NEW explicit pin (dependency audit). pydantic-core is released in
# lockstep with pydantic and pydantic 2.13.4 requires pydantic-core==2.46.4
# exactly — pinning it directly here (rather than leaving it to transitive
# resolution) keeps the lock fully deterministic.
pydantic-core==2.46.4

# CHANGED 3.4.0 -> 3.5.0 (dependency audit). 3.4.0 requires
# `pyasn1<0.5.0,>=0.4.1`, but google-genai's google-auth dependency pulls in
# pyasn1-modules>=0.6.1, which itself requires `pyasn1<0.7.0,>=0.6.1` — the
# two chains cannot both be satisfied under jose 3.4.0. Upstream jose 3.5.0
# (released 2025-05-28) relaxed this to `pyasn1>=0.5.0` with no upper bound,
# specifically a dependency-metadata change (see project CHANGELOG: "Upgrade
# to pyasn1 0.5.1+") with no public API changes — this app only calls jose's
# public `jwt.encode`/`jwt.decode`/`JWTError`, none of which changed.
PyJWT[crypto]==2.8.0
# NEW explicit pin (dependency audit). Previously only ever resolved
# transitively; pinning it directly because it's the exact point of the
# jose/google-auth conflict above. 0.6.3 satisfies both jose 3.5.0's
# `pyasn1>=0.5.0` and google-auth's pyasn1-modules `pyasn1<0.7.0,>=0.6.1`.
